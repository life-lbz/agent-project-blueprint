# 五份文档：各自必备小节与质量检查点

写每份文档前，先读对应小节。每份 = 回答的核心问题 + 必备小节 + 检查点（全部通过才算完成，通过表附在里程碑小结里）。

**统一规范（所有文档适用）**：
- 小节标题显式编号：`## <文档序号>.<小节序号> <标题>`，比如架构文档里 `## 3.2 技术选型决策表`
- 选型论据必须显式贴引用路径：`（调研来源：需求分析文档 → 参考实例调研 → X 项目）`
- 5 种关键表格的**标准表头模板**见本文档末尾"附录：表格标准表头"

---

## 1. 需求分析文档（回答"为什么做、给谁做、做成什么样"）

- 必备小节：
  - 1.1 项目愿景：业务痛点（谁、什么场景、损失什么）、ROI 估算（量化公式 + 假设来源）、电梯演讲（一句话不超过 50 字，无术语）
  - 1.2 需求规格：功能需求列表（编号 FR-x，每条含输入/处理/输出/优先级）、非功能需求（性能/并发/延迟/可用性，全部量化）、边界条件（不做什么、输入上限）、异常降级方案（模型超时、检索为空、工具失败各自的退路，写明降级后返回什么、提示什么）
  - 1.3 用户画像与场景矩阵：画像（角色/技术熟练度/使用频率/核心诉求）、场景矩阵表（表头见附录）
  - 1.4 成功指标：KPI 表（指标名/目标值/测量方法/采样频率，如准确率>90%、单次 Token 成本<X）
  - 1.5 参考实例调研：3-5 个 GitHub 同类项目，对比表（表头见 research-playbook.md）+ 每个项目一段"对本项目的启示"；搜索关键词、筛选门槛、反例排除规则见 research-playbook.md
- 检查点：痛点有具体场景；ROI 有数字且假设可溯源；每条 FR 可测试；每个外部依赖有降级方案；KPI 口径与 ROI 一致；调研项目真实存在并附链接，每条启示能落地到本项目的一个决策点；场景矩阵用了标准表头。

## 2. Agent 设计文档（回答"Agent 怎么想和做"）

- 必备小节：
  - 2.1 角色定义：单 Agent——能力边界两栏表（能做/不能做）；多 Agent——角色依赖矩阵（表头见附录），每个 Agent 一句话职责
  - 2.2 交互流程与编排：用户↔Agent 对话流程（Mermaid 状态图或流程图 + 状态迁移表：状态/触发/动作/下一状态，覆盖追问、拒答、工具超时等异常分支）；多 Agent 另加通信协议选型（直接对话/消息队列/黑板）与编排模式（顺序/层级/swarm），各给选型理由
  - 2.3 Prompt 工程规范：System Prompt 模板骨架（角色/任务/约束/输出格式/工具使用规则，模板本体放附录）、**版本管理规则（具体如下）**、变量注入规则表（变量/来源/转义与防注入处理）、Few-shot 示例集（≥3 条，含至少 1 条反例）
    - **Prompt 版本管理具体化**：版本号格式 `v<主>.<次>-<日期>`（如 `v1.2-2026-11-10`）；每次变更必须关联 git commit，commit message 格式 `[prompt] <变更说明>`；回滚用 `git revert <旧 commit>`，版本号回退且主号 -1
  - 2.4 工具清单：工具总表（表头见附录）
- 检查点：依赖矩阵若有环写明处理策略；Mermaid 图与状态迁移表内容一致；模板每个变量都能在注入表中找到；写操作类工具默认需审批；每个工具都有失败路径；Prompt 版本号格式合规。

## 3. 架构与技术实现文档（回答"用什么做、怎么搭"）

- 必备小节：
  - 3.1 系统整体架构：Mermaid 分层图（接入层/编排层/能力层/数据层/基础设施）+ 各层职责文字说明
  - 3.2 技术选型决策表：候选 A/B/C、最终选择、理由、为什么不选其他；**每行必须显式贴调研引用**（如 `（调研来源：需求分析文档 → 参考实例调研 → X 项目）`）；选型对比表头见附录
  - 3.3 RAG 与知识库设计：数据源清单（来源/格式/更新频率/负责人）、分块策略（块大小/重叠/结构还是语义/理由）、向量库选型对比表、检索+重排方案（召回数/重排模型/混合检索权重）、端到端检索质量测量方法；无 RAG 需求写"不适用"+理由
  - 3.4 模型选型：LLM 与 Embedding 对比表（候选/能力/上下文长度/单价/延迟）、关键参数及理由、月度 Token 成本估算（表头见附录，每步假设写明）、主模型与备份模型
  - 3.5 API 接口规范：端点清单与请求/响应字段表、错误码表、版本管理（路径或请求头版本、废弃策略）、限流策略（维度/配额/超限响应）；纯内部项目可精简，说明理由
  - 3.6 部署方案：环境、资源规格、伸缩策略
- 检查点：架构图与文字说明一致；决策表每行有"不选其他"的具体原因且**引用能 grep 到需求分析文档调研章节**（用户可验证）；成本估算有公式有数字，与可行性分析文档一致；显存/部署约束（来自第一步用户选择）已纳入选型条件；每个端点有错误码与限流说明。

## 4. 前端设计文档（回答"界面用什么做、长什么样"）— 仅当用户需要前端时生成

- 必备小节：
  - 4.1 技术选型：默认基线 React + TypeScript + AntDesign；管理后台类项目对比 VbenAdmin（Vue3 + Vite）后二选一，对比表写明"为什么不选另一套"
  - 4.2 工程结构：目录组织、状态管理、路由方案
  - 4.3 页面清单：页面/路由/对应的功能需求编号（FR-x）/核心交互
  - 4.4 核心页面布局：关键页面的文字线框或 Mermaid 示意 + 布局说明
  - 4.5 组件设计：自定义组件清单（名称/职责/props 要点）
  - 4.6 前后端对接：页面 ↔ API 端点映射表（端点来自架构文档 3.5）
- 检查点：页面清单覆盖需求分析文档的全部 FR（或说明哪些 FR 无界面）；API 映射表与架构文档端点一致。

## 5. 可行性分析文档（回答"能不能做成、怎么防止搞砸、怎么证明做好了"）

- 必备小节：
  - 5.1 技术可行性：关键技术风险清单（风险/影响/验证方式/预案）
  - 5.2 安全设计：Prompt 注入防护（输入过滤/指令隔离/输出校验）、敏感信息过滤（类型清单/检测方式/处置动作）、权限分级表（角色 × 可调用工具 × 可访问数据，覆盖所有写操作工具）
  - 5.3 可观测性：全链路 Trace 方案（TraceID 贯穿、关键 span）、关键埋点表（事件名/触发点/字段）、幻觉率采样方案（采样比例/评估方式/处置阈值数值）、告警策略（指标/阈值/通知渠道，阈值与需求分析 1.4 KPI 联动）
  - 5.4 成本与合规：Token 预算日/月上限与超限自动动作（降级/熔断/通知，不是"人工关注"）、数据法规（适用法规/数据驻留/用户授权）、开源许可证审计（依赖清单覆盖模型、框架、向量库）
  - 5.5 测试策略：单元/集成/回归三层方案、Golden Set 自动化机制（Prompt 或模型变更后自动跑全量、通过门槛数值、回归失败处理流程）
  - 5.6 Golden Set 首批用例：文档内 5-10 条示例 + 同目录 `GoldenSet首批用例.jsonl`；**jsonl 字段规范**：
    ```
    id: 唯一标识
    场景编号: 来自需求分析文档 1.3 场景矩阵
    输入: 原始用户输入
    标准答案: 具体值（三选一类型之一）
    答案类型: exact_match | candidate_set | semantic_match
    评分阈值: exact_match=布尔 | candidate_set=布尔 | semantic_match=余弦相似度阈值（如0.85）
    难度: easy | medium | hard
    ```
    - `exact_match`：模型输出与标准答案精确字符串匹配即为通过
    - `candidate_set`：标准答案是候选列表，模型输出在列表中即为通过
    - `semantic_match`：标准答案是一段文本，用 embedding 余弦相似度 > 阈值即为通过
- 检查点：成本数字与架构文档口径一致；告警阈值引用 KPI 数值；幻觉处置阈值有具体数值；Golden Set 用例覆盖场景矩阵的每类场景；jsonl 文件真实存在、字段齐全、每条都有答案类型和评分阈值。
